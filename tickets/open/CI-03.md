# CI-03 · Drop the CodeQL Kotlin compiler pin once the bundle supports 2.4.20

**Priority:** P3
**Effort:** ~0.5 d
**Skills:** `critical-invariants.md` + `secure-coding.md`

## Motivation / context

FIX-03 restored the `java-kotlin` CodeQL lane by compiling the analysis build with Kotlin 2.4.10,
the newest compiler CodeQL 2.27.0's extractor accepts. That is a detour around a gap upstream, not a
property of this repository, and it should not outlive the gap. The ticket exists because the
trigger is an external release — the **external dependency** row of PROJECT_MANAGEMENT § 8 — and no
edit here can bring it forward.

## Current state (honest)

`backend/settings.gradle.kts` lets the catalogue's `kotlin` version be overridden by the Gradle
property `codeqlKotlinVersion`. Exactly one caller sets it: the `Build for analysis` step in
`.github/workflows/codeql.yml`, at `2.4.10`. Every other build — CI, release, a laptop — resolves
the catalogue's own version, so the shipped artefacts are unaffected and CVE-2026-53914 stays fixed.

The detour is bounded and fails loudly rather than quietly: if the source ever uses a language
feature 2.4.10 does not have, the analysis build breaks and the lane goes red. It cannot go green
while analysing nothing, which is the failure this pin was introduced to end.

Support for 2.4.20 is merged upstream — the extractor's version-check fixture names 2.4.30 as the
cap — and ships in the bundle after 2.27.0. Dependabot proposes the `codeql-action` bump in its
weekly actions group, so the trigger arrives as a pull request.

The analysis job itself therefore runs the Kotlin Gradle plugin that still carries
CVE-2026-53914. What the advisory reaches is build-cache metadata, and `codeql.yml` uses neither
`setup-gradle` nor any cache action: the only build cache that job has is the one it creates inside
itself and discards with the runner. Written down here rather than left to be re-derived.

## Approach

1. When a `codeql-action` release bundling CodeQL > 2.27.0 lands, read the bundle's Kotlin cap.
2. If it covers the catalogue's Kotlin version: delete `-PcodeqlKotlinVersion=…` **and the two
   comment lines above it** from the workflow step, and the `versionCatalogs` block with its comment
   from `backend/settings.gradle.kts`. Left behind, the comment claims a constraint the step no
   longer carries — which is worse than no comment.
3. Push the branch and confirm the `Analyse (java-kotlin)` job reaches the `Analyse` step and
   uploads a real result, not a failed-run SARIF.
4. If the cap still trails the catalogue, raise the pinned version to the new cap instead of
   deleting, and say so here.

## Acceptance criteria

- [ ] No `codeqlKotlinVersion` property remains in the workflow or in `backend/settings.gradle.kts`,
      or the ticket records why the pin had to be raised rather than removed.
- [ ] The `java-kotlin` job compiles with the catalogue's own Kotlin version and completes the
      `Analyse` step.
- [ ] `make check` green.
- [ ] Independent review (phase 4, run in a sub-agent): 0 BLOCKING findings.

## Affected files

- `.github/workflows/codeql.yml` — the property and the comment lines explaining it leave together.
- `backend/settings.gradle.kts` — the override block and its comment go with it.

## Verification

The check is the CodeQL run on the branch: `Analyse (java-kotlin)` reaches `Analyse` and the run
uploads an analysis rather than a failed-run SARIF. `gh run view <id> --log` names the step that
proves it. No local test environment is needed; the backend lanes are unaffected.
