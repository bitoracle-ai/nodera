# CI-02 · Make the repository's own runs leave nothing behind

**Priority:** P3
**Effort:** ~0.5 d
**Skills:** `critical-invariants.md` + `testing.md` + `database-design.md`

## Motivation / context

[DOC-06](../closed/DOC-06.md) wrote down the rule that a check needing more than this repository's
toolchain runs in an environment created for that run and torn down afterwards. Its phase-4 review
found that one of the mechanics it had named as satisfying the rule does not: `make verify-db`
depends on `up`, so it runs inside the developer's Postgres.

The rule is right; the target has not caught up with it. `skills/testing.md` names the gap in place
rather than pretending otherwise, and this is the package that closes it.

**And it takes the second run of the same shape, rather than leaving it for a third ticket**
(§ 8: widen rather than file). `scripts/verify_image.sh` removes its containers and its network in a
trap, but `docker rm -f` without `-v` leaves the anonymous volume the Postgres image declares — one
dangling volume per run. Its header comment says so now; this package makes it true instead.

**Why this is its own package and the rule was not simply widened to accommodate the target**
(`docs/PROJECT_MANAGEMENT.md` § 8): the fix is a change to the `Makefile`, which is a different
kind of change from the documentation package that found it — it has its own gates, it changes what
every contributor's `make verify-db` does, and CI's own database lane must keep matching it. A
documentation package editing the build to make its own sentence true is the scope creep § 8's
foreign-subtree row exists to refuse.

## Current state (honest)

`verify-db: up` in the `Makefile`. The recipe drops and recreates `nodera_verify` inside the compose
Postgres, applies the migration sequence twice, runs `db/checks/schema_integrity.sql` and drops the
database again. Three consequences, none of them wrong today but none of them stated by the target:

1. It **starts** the developer's Postgres container if it was stopped, and leaves it running. There
   is no `down` in the recipe.
2. `nodera_verify` lives in the same cluster, so its files are written into the volume behind
   `make up` and removed with the database.
3. `V4` creates the cluster-level role `nodera_app` (`if not exists`). Roles are not database-level,
   so the role survives the `drop database` and stays in the developer's cluster.

In CI none of this applies: `.github/workflows/ci.yml` gives the database job its own
`services: postgres` container, which the runner discards with the job. The divergence is between
the CI lane and its documented local equivalent — the thing `docs/ci.md` exists to keep true.

## Approach

1. Run the target under its own compose project name rather than the default (`docker compose -p …`,
   the shape `docs/ops/backup-restore.md` § The drill already uses), so it never resolves to the
   volume `make up` uses. **`-p` alone will not do it:** `docker-compose.yml` pins
   `container_name: nodera-postgres`, which is project-independent, so a second project collides
   with a running `make up` container — the drill escapes this only by running `compose.prod.yml`.
   This target needs its own compose fragment, or the pinned name has to go.
2. Tear it down at the end, including the volume, on success **and** on failure — a target that
   leaves a container behind when a migration fails is the case that matters.
3. `scripts/verify_image.sh`: `docker rm -f -v` in its `cleanup()`, and the header comment goes back
   to the plain claim. One character of behaviour, proved by comparing `docker volume ls` across a
   run.
4. Keep `make check` unchanged in cost: `check-db` does not run `verify-db` today, and this package
   does not change that.
5. Update `docs/ci.md`, `skills/testing.md` and `db/migrations/CLAUDE.md` + `AGENTS.md` — the
   sentences that currently name the gap say the plain thing once it is gone.
6. The `Makefile`'s own words move with the target. Three places: the block comment above
   `verify-db`, ending "running it costs nothing and destroys nothing" — true of the database, an
   overstatement about the container and the `nodera_app` role; and the header comment and the
   `check` help string, both of which say `make check` runs what CI runs, when it does not run
   `verify-db`. [DOC-06](../closed/DOC-06.md) qualified those sentences everywhere outside the
   build and left these here rather than editing the build from a documentation package.

## ⚠️ To decide before starting

- **Whether `verify-db` should still be a one-command target.** Standing up a second Postgres costs
  a few seconds per run. The alternative — keeping the developer's container and only isolating the
  database, as today — is what this package exists to replace, so the recommendation is to pay it.

## Acceptance criteria

- [ ] `make verify-db` creates its own container under a dedicated compose project name, and removes
      the container, its volume and its network afterwards — verified by `docker ps -a` and
      `docker volume ls` being unchanged before and after a run.
- [ ] A run with the developer's stack stopped leaves it stopped, and `nodera_app` is not added to
      the developer's cluster.
- [ ] A **failing** migration also leaves nothing behind.
- [ ] `sh scripts/verify_image.sh` leaves no dangling volume — `docker volume ls` identical before
      and after.
- [ ] `docs/ci.md`, `skills/testing.md` and the `db/migrations/` scoped pair no longer describe the
      target as an exception to the rule.
- [ ] The `Makefile` describes what it now does: the comment above `verify-db`, and the header
      comment and `check` help string that currently say `make check` runs what CI runs.
- [ ] `make check` green.
- [ ] Independent review (phase 4, run in a sub-agent): 0 BLOCKING findings.

## Affected files

- `Makefile` — the `verify-db` target, whatever it needs to tear itself down, and the help string
  and block comment that describe it.
- `scripts/verify_image.sh` — the `cleanup()` removal, and the comment DOC-06 corrected.
- `docs/ci.md` · `skills/testing.md` · `db/migrations/CLAUDE.md` · `db/migrations/AGENTS.md` — the
  descriptions that currently name the gap.

## Verification

`make PY=py verify-db` twice: once with the developer's stack up, once with it stopped. Before and
after each, compare `docker ps -a`, `docker volume ls` and `docker network ls`, and check the
developer's cluster for `nodera_app` with `psql -c '\\du'`. Then a deliberately failing migration, to
prove the teardown runs on the path nobody tests.
