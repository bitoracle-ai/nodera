# CI-02 · Make the repository's own runs leave nothing behind

**Priority:** P3
**Effort:** ~0.5 d
**Skills:** `critical-invariants.md` + `testing.md` + `database-design.md`

## Motivation / context

[DOC-06](DOC-06.md) wrote down the rule that a check needing more than this repository's
toolchain runs in an environment created for that run and torn down afterwards. Its phase-4 review
found that one of the mechanics it had named as satisfying the rule does not: `make verify-db`
depends on `up`, so it runs inside the developer's Postgres.

The rule is right; the target has not caught up with it. `skills/testing.md` names the gap in place
rather than pretending otherwise, and this is the package that closes it.

**And it takes the second run of the same shape, rather than leaving it for a third ticket**
(§ 8: widen rather than file). `scripts/verify_image.sh` removes its containers and its network in a
trap, but `docker rm -f` without `-v` leaves the anonymous volume the Postgres image declares — one
dangling volume per run. Its header comment says so now; this package makes it true instead.

**Why this is its own package and the rule was not simply widened to accommodate the target**
(`docs/PROJECT_MANAGEMENT.md` § 8): the fix is a change to the `Makefile`, which is a different
kind of change from the documentation package that found it — it has its own gates, it changes what
every contributor's `make verify-db` does, and CI's own database lane must keep matching it. A
documentation package editing the build to make its own sentence true is the scope creep § 8's
foreign-subtree row exists to refuse.

## Current state (honest)

`verify-db: up` in the `Makefile`. The recipe drops and recreates `nodera_verify` inside the compose
Postgres, applies the migration sequence twice, runs `db/checks/schema_integrity.sql` and drops the
database again. Three consequences, none of them wrong today but none of them stated by the target:

1. It **starts** the developer's Postgres container if it was stopped, and leaves it running. There
   is no `down` in the recipe.
2. `nodera_verify` lives in the same cluster, so its files are written into the volume behind
   `make up` and removed with the database.
3. `V4` creates the cluster-level role `nodera_app` (`if not exists`). Roles are not database-level,
   so the role survives the `drop database` and stays in the developer's cluster.

In CI none of this applies: `.github/workflows/ci.yml` gives the database job its own
`services: postgres` container, which the runner discards with the job. The divergence is between
the CI lane and its documented local equivalent — the thing `docs/ci.md` exists to keep true.

## Approach

1. Run the target under its own compose project name rather than the default (`docker compose -p …`,
   the shape `docs/ops/backup-restore.md` § The drill already uses), so it never resolves to the
   volume `make up` uses. **`-p` alone will not do it:** `docker-compose.yml` pins
   `container_name: nodera-postgres`, which is project-independent, so a second project collides
   with a running `make up` container — the drill escapes this only by running `compose.prod.yml`.
   This target needs its own compose fragment, or the pinned name has to go.
2. Tear it down at the end, including the volume, on success **and** on failure — a target that
   leaves a container behind when a migration fails is the case that matters.
3. `scripts/verify_image.sh`: `docker rm -f -v` in its `cleanup()`, and the header comment goes back
   to the plain claim. One character of behaviour, proved by comparing `docker volume ls` across a
   run.
4. Keep `make check` unchanged in cost: `check-db` does not run `verify-db` today, and this package
   does not change that.
5. Update `docs/ci.md`, `skills/testing.md` and `db/migrations/CLAUDE.md` + `AGENTS.md` — the
   sentences that currently name the gap say the plain thing once it is gone.
6. The `Makefile`'s own words move with the target. Three places: the block comment above
   `verify-db`, ending "running it costs nothing and destroys nothing" — true of the database, an
   overstatement about the container and the `nodera_app` role; and the header comment and the
   `check` help string, both of which say `make check` runs what CI runs, when it does not run
   `verify-db`. [DOC-06](DOC-06.md) qualified those sentences everywhere outside the
   build and left these here rather than editing the build from a documentation package.

## ⚠️ To decide before starting

- **Whether `verify-db` should still be a one-command target.** Standing up a second Postgres costs
  a few seconds per run. The alternative — keeping the developer's container and only isolating the
  database, as today — is what this package exists to replace, so the recommendation is to pay it.

## Acceptance criteria

- [x] `make verify-db` creates its own container under a dedicated compose project name, and removes
      the container, its volume and its network afterwards — verified by `docker ps -a` and
      `docker volume ls` being unchanged before and after a run. `compose.verify.yml` under
      `-p nodera-verify`: `nodera-verify-postgres-1`, `nodera-verify_pgdata` and
      `nodera-verify_default` created and removed on every run, with `docker ps -a`,
      `docker volume ls` and `docker network ls` diffing identical against the pre-run snapshot.
- [x] A run with the developer's stack stopped leaves it stopped, and `nodera_app` is not added to
      the developer's cluster. `up` is no longer a prerequisite. Run once with `nodera-postgres`
      absent — it stayed absent — and once with it up: that cluster returned the same roles and the
      same four databases before and after, and the container was still up and healthy. `nodera_app`
      was **already** in that cluster from the old target and was left alone (§ Operator note).
- [x] A **failing** migration also leaves nothing behind. A temporary `V7` referencing a
      non-existent table: `BUILD FAILED`, the trap removed container, volume and network, and make
      reported `Error 1` — the teardown does not mask the failure.
- [x] `sh scripts/verify_image.sh` leaves no dangling volume — `docker volume ls` identical before
      and after. Run against `nodera:local`: 14 passed, 0 failed, with the container, volume and
      network sets identical.
- [x] `docs/ci.md`, `skills/testing.md` and the `db/migrations/` scoped pair no longer describe the
      target as an exception to the rule. Neither does any other file (§ Review result).
- [x] The `Makefile` describes what it now does: the comment above `verify-db`, and the header
      comment and `check` help string that said `make check` runs what CI runs.
- [x] `make check` green — `make PY=py check` returned `All gates green.` Which lanes actually
      executed is in § Review result.
- [x] Independent review (phase 4, run in a sub-agent): 0 BLOCKING findings. Two rounds.

**Two adjacent fixes in `scripts/verify_image.sh`**, kept here rather than filed

1. `export MSYS_NO_PATHCONV=1`. Git Bash rewrote `--tmpfs /tmp` into a host path, so the `serve`

   PASS for a check whose container did not exist. With it, 14 / 0. No argument in the script relies
   on the conversion being on.
2. That SIGTERM check required only that the stop returned inside the grace period, so it printed
   **PASS for a container that never started.** It now requires the container to have been running
   and to yield an exit code.

## Verification

`make PY=py verify-db` twice: once with the developer's stack up, once with it stopped. Before and
after each, compare `docker ps -a`, `docker volume ls` and `docker network ls`, and check the
developer's cluster for `nodera_app` with `psql -c '\\du'`. Then a deliberately failing migration, to
prove the teardown runs on the path nobody tests.

All of it was run; the record is § Review result. Two guards were additionally put on trial rather
than asserted, because both fail silently:

- **`-p` is load-bearing.** `COMPOSE_PROJECT_NAME=nodera docker compose -f compose.verify.yml config`
  resolves to project `nodera` and volume `nodera_pgdata` — the developer's data volume, which the
  recipe's first command (`down -v`) would then delete. Precedence is `-p` > `COMPOSE_PROJECT_NAME` >
  the file's `name:`, so the file's own name is not the guard. Proved at runtime as well, with a
  harmless `COMPOSE_PROJECT_NAME` set: the run still created and removed `nodera-verify_pgdata`, and
  `nodera_pgdata` was untouched.
- **The signal trap must exit, not return.** With `trap … EXIT INT TERM`, a `SIGTERM` ran the
  teardown and the shell then **carried on** — finishing the remaining steps against an environment
  that no longer existed, and exiting 0. Split into `trap … EXIT` plus `trap 'exit 130' INT TERM`,
  the same signal tears down once and exits 130. Both halves were watched.

## Operator note

The developer's cluster on the machine this ran on already carried the cluster-level `nodera_app`
role, left there by the old target before this package existed. It was left exactly as found:
removing it changes the operator's own state, which is not this package's to change, and nothing
here depends on it either way. A fresh clone never acquires it, because the run no longer touches
that cluster.

## Review result

**Two independent sub-agent rounds. Round 1: CHANGES REQUIRED, 1 BLOCKING, 5 NON-BLOCKING.
Round 2, on the fixed diff: APPROVED, 0 BLOCKING, 3 NON-BLOCKING.** Every finding of both rounds is
fixed. Neither reviewer wrote any of the code.

**The blocking one was a data-loss defect in the isolation this package exists to provide.** The
first implementation gave the fragment a `name: nodera-verify` key and passed no `-p`. Compose
resolves the project name `-p` > `COMPOSE_PROJECT_NAME` > the file's `name:`, so a developer with
`COMPOSE_PROJECT_NAME=nodera` exported — the development project's own name — would have had the
recipe's **first** command, `down -v --remove-orphans`, resolve to the development project and
delete `nodera_pgdata`. The target written to stop touching the developer's database would have
destroyed it. The fix is `-p nodera-verify` on `VERIFY_COMPOSE`; both directions were then watched,
because a guarantee nobody has seen fail is an assertion.

The lesson generalises past this target: **the compose file's own `name:` is not an isolation
guard.** It is the weakest of the three inputs, and the environment silently outranks it.
[`../../docs/ops/backup-restore.md`](../../docs/ops/backup-restore.md) § The drill had already
learned this — it overrides `compose.prod.yml`'s `name: nodera` with `-p nodera-drill` rather than
trusting it — and the first draft here did not carry the lesson across.

**Round 1's other findings**, all fixed: the fixed host port 55432 was already taken on the machine
the reviewer ran on, so the published port is now ephemeral, bound to loopback and read back with
`docker compose port` (`NODERA_VERIFY_PORT` still pins one); `docs/ci.md` claimed more than its
layer-2 source by omitting the limit both mechanics share — the base image stays in the local image
cache; the SIGTERM check in `scripts/verify_image.sh` still passed for a container that had started
and died before the stop; and the hand-maintained head of
[`../INDEX.md`](../INDEX.md) still stated the retired claim in the present tense.

**Round 2's three**, all fixed: `trap … EXIT INT TERM` installs a handler that *returns*, so a
`SIGTERM` tore the environment down and the recipe then carried on against it and exited **0** — the
teardown was right and the abort was not. Split into `trap … EXIT` plus `trap 'exit 130' INT TERM`.
The database name, owner and password were maintained twice, in the `Makefile` and in the fragment;
they are declared `:?` in the fragment now, the shape `compose.prod.yml` uses, so the `Makefile` is
their one source and a hand-run refuses by naming the variable. And the CHANGELOG recorded two of
the three `scripts/verify_image.sh` changes.

**The distillate sweep.** DOC-06's record is that a rule stated once reached nine files by hand and
six review rounds each found one more copy. Nine files carried this one, and
`scripts/lint_adapters.py` reads only three of them. Both reviewers ran their own tree-wide sweep;
between them they found two survivors this package had missed — the `note:` frontmatter of this
ticket, which generates the INDEX table row, and the INDEX head. Everything under
`tickets/closed/` still describes the old behaviour and was deliberately left: those are records of
what was true when they were written.

### Gates, and which lanes actually ran

`make PY=py check` → `All gates green.` Not all of it executed, and the distinction matters here:

- **Repository and database lanes: executed.** All thirteen checks, including both paired-negative
  self-tests (`lint_invariants.py --self-test`, 20 fixtures; `lint_sql.py --self-test`, 5).
- **Frontend lane: executed.** 3 files, 15 tests, per-file coverage, typecheck, build.
- **Backend lane: satisfied without executing a test.** `74 actionable tasks: 1 executed, 73
  up-to-date`, and every `test` task `UP-TO-DATE` — the CORE-06 shape, stated rather than reported
  as passing tests. Correct here: this package changes no Kotlin, and nothing in it rests on the
  backend suite.
- **What this package does rest on, and what was executed for it:** `make PY=py verify-db` five
  times — with the developer's stack absent, with it running, with a `COMPOSE_PROJECT_NAME` set, and
  twice against a deliberately broken migration — each applying the six migrations, re-applying them
  as a no-op, and running `db/checks/schema_integrity.sql`. Plus `sh scripts/verify_image.sh
  nodera:local`, 14 passed / 0 failed, twice.
- **Not run:** `gitleaks` (CI-only, as always), and CI itself. CI's `database` job was deliberately
  not changed; the local recipe now matches it more closely than before, because it connects as
  `nodera_owner` where it used to connect as `nodera`.

### What the runs created and removed

Every run created the compose project `nodera-verify` — container `nodera-verify-postgres-1`, volume
`nodera-verify_pgdata`, network `nodera-verify_default` — and removed all three. `docker ps -a`,
`docker volume ls` and `docker network ls` were captured before the first run and diffed identical
after the last. `make up` was started once to prove the no-collision case and removed again with
`make down`; the volume behind it, `nodera_pgdata`, was never written to and is the one thing that
survives on purpose. Nothing was left running. The `postgres:16-alpine` image stays in the local
cache, which is the named limit rather than an exception to the rule.
