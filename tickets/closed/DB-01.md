# DB-01 · Apply the baseline schema and prove row-level security with negative tests

**Priority:** P1
**Effort:** ~2 d

## Motivation / context

The migrations apply, but nothing they claim to enforce has ever been observed failing. Until a
negative test is demonstrably red with the guard removed, every invariant they carry — the
append-only audit grant, the RLS policies, the ownership chain trigger — is a claim in a file. A
schema that has run is not yet a schema that holds.

## Current state (honest)

`V1` to `V5` exist and apply. OPS-01 replaced the Flyway Gradle plugin with the `migrate`
entrypoint, wired the `nodera_app_password` placeholder, and made the CI database lane apply the
sequence twice against an empty Postgres — so "applies without error" is already covered, and this
package is now about proof rather than execution. No Testcontainers harness exists, and no policy
or trigger here has ever been seen to refuse anything.

`scripts/lint_sql.py` exists and its checksum ledger is armed: `V1` to `V5` are recorded in
`db/migrations/.checksums` and are frozen. They are applied durably in every contributor's
`make dev` database, so a correction found while proving the schema is a **new** migration, never
an edit to one of these five.

## Approach

1. Build the Testcontainers harness in `:persistence` — a real Postgres 16, migrations applied
   once per test class.
2. Reach each guard through the application role, not the owner: a policy the owner bypasses is a
   policy that was never under test.
3. Write one negative test per enforced rule: RLS on each project-scoped table, the append-only
   audit triggers, actor-kind immutability, the agent-ownership chain, the dependency-cycle trigger
   and reviewer independence.

## Acceptance criteria

- [x] Every RLS policy has a test that is demonstrably red when the policy is dropped; both outcomes
      are recorded in the review result. **Fourteen policies, and the removal is deliberately not a
      `drop policy`** — an RLS-enabled table with no policy denies everything, so a dropped-policy
      probe reads the same zero the working guard reads and would leave a negative that passes with
      the guard gone. The two removals used instead are `disable row level security` (the mechanism)
      and `alter policy <t>_visible … using (true)` (the predicate). Drop-policy deny-all is pinned
      by its own test. Two completeness tests bind the covered set to `pg_class.relrowsecurity` and
      to one policy per table, so a future policy cannot go untested in silence.
- [x] `nodera_app` cannot update, delete or truncate `audit_event` — proved by a test asserting the
      failure, not by reading the grant. **Both layers separately.** The grant refuses first, so the
      triggers would never fire and would have stayed as untested as before; each mutation is
      therefore also run with the privilege granted and the trigger still enabled, where the refusal
      carries the trigger's own AU1 message.
- [x] A cross-project read returns **zero rows** rather than an error — asserted as a completing
      query with an empty result set, plus fourteen `count(*)` probes that return 0 rather than raise.
- [x] `scripts/lint_sql.py` passes, and fails on a deliberately quoted mixed-case identifier. Shown
      both ways on the real tree, and committed as `--self-test` so it stays shown — the shape
      CORE-01 established for `lint_invariants.py`.
- [x] No edit to `V1`-`V5`. `git diff` on those five files is empty and the ledger diff is one `+`
      line with no `-` line. The defect found is corrected by **`V6`**.
- [x] `make check` green — `make PY=py check` → `All gates green.`, exit 0. `make PY=py verify-db`
      also green: six migrations applied to an empty database, re-applied as a no-op, and
      `db/checks/schema_integrity.sql` reporting OK.
- [x] Independent review: 0 BLOCKING findings. Three rounds across two independent contexts.
      Rounds 1 and 2 APPROVED at 0 BLOCKING; round 3 returned **CHANGES REQUIRED, 2 BLOCKING** —
      one of them against this ticket having been closed before round 3 returned — and both are
      fixed. The criterion is met on the state being closed now, not on the earlier attempt.

### The defect: `ticket_label` could bind across projects

`ticket_label` was the last two-ended association without a same-project guard. `V4`'s policy scopes
`ticket_id` and says nothing about `label_id`, and referential integrity checks bypass row-level
security by design — they must, or a foreign key could be evaded by hiding the parent. So a caller
holding a context for project A alone could attach a **project B label** to a project A ticket, and
the insert was accepted. Present since `V2` created the table, unguarded since `V4` set the policy.

**What it was not: a cross-project read.** The label's own columns stayed invisible and the join
returned nothing. What it was: a cross-project *write*, and a weak existence oracle — a caller who
already held a label UUID learned it was real, because a genuine id succeeded where an invented one
raised a foreign key violation. `ticket_dependency` has the identical shape and has carried its
trigger since `V2`; that asymmetry is what makes this an omission rather than a decision. Nothing
else in the schema shares the shape — every other association has one end that is global (an actor)
or is already scoped through its parent.

Corrected by **`V6`**, never by editing `V2`. `V6` also refuses to install over pre-existing
straddling rows rather than deleting them, because deleting rows unasked is not a migration's call.

### One judgement worth recording

`V6`'s comments were corrected after `--accept` had already recorded it, so `--accept` ran a second
time and printed its "already recorded and its content has changed" warning. That warning is right to
exist and did not apply here, and the reason is worth stating exactly, because a looser version of it
would be dangerous.

**The freezing event is the commit, not "has it been applied somewhere yet".** From the moment `V6`
lands on the branch, every contributor's next `make dev` applies it, so it is frozen from that moment
whether or not anyone has run it. Until then it is a file in a working tree that no one else can have
applied. `V6` was uncommitted for the whole of this package, so re-recording it was editing an
unreleased migration, not hiding a forward-only violation. Against `HEAD` the ledger still shows one
`+` line and no `-` line. **After this commit, any correction to `V6` — including to a comment — is a
`V7`.**

### What the reviewers could not verify, stated rather than implied

- **No reviewer ran the suite.** Both were instructed not to invoke gradle, make, yarn or docker.
  Every statement above about a test passing is the implementer's run, reported here; the reviewers
  read the code and confirmed that no test in the package stays green with its guard removed.
- **The frontend lane** is untouched by this diff. One full `make check` did go red in it, on
  `frontend/src/invariants.test.ts` — WEB-03's paired negative for invariant F1 — which timed out at
  5 s while the backend build was running beside it. Re-run with nothing else running: 17 passed in
  6.46 s, and `make check` green. The failure is a cold-start cost in the test, not this diff, and
  `frontend/` is a foreign subtree for a `DB-` package, so it is [FIX-02](../open/FIX-02.md) rather
  than a fix here. Recorded because the green above would otherwise read as though the lane had
  never been red.
- **Two limits of `review_independent` are recorded, not fixed** (plan § 4.4): it is `before insert`
  only, so assigning a ticket to someone who already reviewed it is not refused; and the reporter of
  an *assigned* ticket may review it, which is correct — the author of the work is the assignee — but
  narrower than the prose above the trigger.
- **The 16-hop bound binds the written row's chain only** (plan § 4.5), because the trigger is
  `before insert or update of owner_actor_id`. Re-pointing a node higher up does not re-validate its
  descendants, so a chain longer than sixteen hops is reachable without any single write having been
  refused. It fails closed both ways that matter: the bound itself is enforced by the schema, raising
  `check_violation` rather than truncating or warning, and the next write beneath an over-long chain
  is refused. Cycles are unaffected. Making the trigger police descendants is a structural decision,
  not this package's to take.
