## 2. The one thing that decides whether any of this is worth running

**Every guard is reached through `nodera_app`, never through the owner.** The owner in a
Testcontainers Postgres is a superuser: RLS is bypassed for it entirely, and a suite written against
it would pass with every policy deleted. That is not a detail of the harness, it is the harness.

Two mechanisms, deliberately both:

| Path | Used for | Why this one |
|---|---|---|
| A real JDBC connection as `nodera_app` | Every **guard-in-place** assertion | The production path, login and grants included. A claim proved here is proved about what actually runs. |
| The owner connection with `set role nodera_app`, inside a transaction that is rolled back | Every **guard-disabled** probe | DDL is transactional in Postgres, so the guard can be removed, the probe run as the application role, and the removal undone — on one connection, with nothing left behind. Two connections cannot do this: `alter table` takes an access-exclusive lock the second connection would block on, and an uncommitted drop is invisible to it anyway. |

`set role` is only trustworthy if it really subjects the session to RLS, so the harness does not
assume it. **Every RLS case runs the same probe three times through the same mechanism** — once with
no DDL at all, then with each of the two guard removals in § 4.2 — and the no-DDL run must return
zero rows. If `set role` did not subject the session to RLS, that control run would return the
foreign row and the whole file would go red rather than quietly green. The control is the reason to
believe the negatives.

**The trigger cases do not carry a control run and do not need one.** Whether RLS applies at all
depends on the effective role, which is what the control rules out; a trigger and a privilege check
bind any session that reaches the statement. Their pairing is the refusal through a real `nodera_app`
login against the acceptance with the guard disabled.

The rollback carries the same burden, so it is asserted rather than assumed: the last test in each
of the two probe-heavy specs re-runs the boundary through a real application connection after every
guard has been removed and restored. A rollback that did not happen leaves a readable cross-project
row, or a rewritable audit trail, and that test is where it surfaces.

### The container

One Postgres 16 per JVM, `by lazy`, migrations applied once through the production `Migrator` in
`:persistence` main — not through a second Flyway configuration written for tests. A test harness
that applies migrations its own way proves the migrations apply *that* way. Reaped by Ryuk.

"Once per JVM" is stronger than the ticket's "once per test class", not weaker: three spec classes
share one migrated database. Isolation comes from every test seeding its own actors, projects and
tickets under fresh UUIDs, so no test can observe another's rows and nothing depends on order.

## 4. The tests

### 4.1 One negative per enforced rule

The ticket enumerates six families. Two more enforced rules live in the same three migration files
and would otherwise be the only untested guards in files that are otherwise fully proved, so they
are covered here rather than left for a follow-up ticket nobody would run
(`PROJECT_MANAGEMENT.md` § 8 — fix-now-or-drop, and the ticket test does not carry either of them):

| Guard | Where | Negative |
|---|---|---|
| RLS, 14 project-scoped tables | `V4` | A row in another project is invisible; the same row is visible with RLS off. |
| `audit_event` cannot be updated / deleted / truncated | `V4` grant + triggers | Both layers, separately. § 4.3 |
| `actor.kind` is immutable | `V1` | `update actor set kind` refused; permitted with the trigger disabled. |
| The agent ownership chain terminates at a human, without cycles | `V1` | Cycle, orphaned chain, missing owner, and the 16-hop bound. |
| The ticket dependency graph is acyclic | `V2` | Two-node and three-node cycles. |
| A dependency does not cross projects | `V2` | *(adjacent)* Cross-project edge refused. |
| The reviewer is not the author | `V3` | Assignee refused; reporter of an unassigned ticket refused. |
| `review` rows are append-only | `V3` | *(adjacent, same family as the audit triggers)* Update and delete refused. |
| A reply stays inside its own ticket | `V3` | *(adjacent)* Cross-ticket reply refused. |

Each family's paired negative removes **the trigger**, once, rather than removing each branch —
the branches are the same guard reached by different inputs, and disabling it once is what
demonstrates the guard is what refuses them.

### 4.2 RLS: what "the guard removed" has to mean

`drop policy ticket_visible on ticket` leaves `ticket` with RLS enabled and no policy, and Postgres
then denies every row to `nodera_app`. The cross-project read still returns zero, so the test still
passes — a paired negative that stays green with the guard gone is the exact shape this repository's
honesty rule exists to catch. It would have been an easy and entirely convincing mistake.

So each table gets **two** guard-removed probes, because they answer different questions:

- `alter table <t> disable row level security` — RLS off entirely. Proves the mechanism is what
  filters, and is the removal that can actually produce a leak.
- `alter policy <t>_visible on <t> using (true)` — RLS still on, predicate replaced. Proves the
  **predicate** is what filters, which is the claim the ticket's wording is really about.

The drop-policy behaviour is pinned by its own test instead of used as a negative: **with the only
policy dropped, `nodera_app` reads zero rows of its own project too.** That is fail-closed stated as
a fact rather than as a preference.

Two completeness tests keep the file from falling behind the schema in silence: the set of tables
covered here must equal the set of tables with `relrowsecurity`, and each must carry exactly the one
policy the negative replaces. A table that gains row-level security without gaining a case here fails
the suite rather than going unproved — which is what "every RLS policy has a test" has to mean if it
is to stay true after this package.

Two further polarity tests, both criteria of the ticket:

- **A cross-project read returns zero rows, not an error.** Asserted as a successful query with an
  empty result set — an exception here would mean the boundary is loud-but-permissive, telling a
  caller that the row exists.
- **With no project context**, every scoped table reads zero rows — asserted twice, because
  `current_project_ids()` has two branches and they are not the same path. `set_config` never called
  is the forgotten-context path; `set_config` called with an empty string is the established-but-empty
  one. They share a result today, and a later edit that splits them would otherwise split in silence.

Each of the fourteen tables is probed by primary key against a row seeded in a **second** project, so
a zero can never come from an empty table; the same row in the caller's own project is asserted
visible in the same test.

### 4.3 `audit_event`: two layers, proved separately

`nodera_app` holds `insert, select` and nothing else, and the table additionally carries
`before update` / `before delete` / `before truncate` triggers. The privilege refuses first, so the
triggers never fire for the application role and a naive test proves only the grant — leaving the
belt-and-braces layer as untested as it was before.

Each of update, delete and truncate is therefore run three times:

1. as `nodera_app` — refused, `42501`, by the missing privilege;
2. with the privilege **granted** and the trigger still enabled — refused, `42501`, by the trigger,
   whose message names invariant AU1;
3. with the privilege granted **and** the trigger disabled — succeeds.

Step 3 is the demonstrable red. Step 2 is the one that makes the second layer a guard rather than a
comment, and it is only reachable because the transaction is rolled back afterwards.

### 4.4 Reviewer independence, as it is actually written

`review_reviewer_is_independent()` refuses the assignee always, and the reporter only when the
ticket is unassigned. So the reporter of a ticket assigned to someone else **may** review it. That
is correct — the author of the work is the assignee, and a reporter reviewing another actor's work
is ordinary — but it is narrower than the prose above the trigger, which says "neither the author nor
the current assignee". The behaviour is pinned by a test that states it, so the next reader meets the
rule rather than inferring it from the comment.

Two limits are recorded rather than changed, because both are structural and neither is this
package's to decide (§ 8):

- The trigger is `before insert` only. Assigning a ticket to an actor who already reviewed it is not
  refused; R1 holds at review time, not thereafter.
- An agent reviewing a human's ticket is asserted to be accepted. Nothing in the schema could refuse
  it — which is the point of invariant #1, and worth a committed test precisely because it is the
  kind of thing a later "safety" change would break without noticing.

### 4.5 What the 16-hop bound actually binds

Raised by phase-4 review, and recorded rather than changed. `agent_owner_chain_is_valid` is declared
`before insert or update of owner_actor_id`, so it walks **the written row's** chain and no other. A
node near the root of one chain can be re-pointed under the tip of another, and its descendants are
not re-validated — so a chain longer than sixteen hops is reachable without any single write ever
having been refused.

It fails closed in both directions that matter. The bound itself is in the schema, not in the test:
the trigger raises `check_violation` at `hops > 16`, so the write is refused rather than truncated or
warned about. And a chain that got long by re-pointing stays refused for every later write beneath it,
because the next insert walks past sixteen hops and raises; `db/checks/schema_integrity.sql` bounds
its own recursion at sixteen too and reports those agents as never reaching a human. **Cycles are not
affected** — re-pointing a node under its own descendant is caught, because the walk from the new
owner reaches the row being written.

Making the trigger re-validate descendants means policing a graph from a row-level trigger, which is
a structural decision about how far the schema should go, not a correction this package can make.

## 5. `lint_sql.py --self-test`

The criterion is that the gate "passes, and **fails** on a deliberately quoted mixed-case
identifier". A demonstration run once in a session and written into a review result decays the day
the regex is touched, and this repository has already been bitten three times by exactly that shape:
the executable bit in CI-01, the module boundary check in OPS-01, and the ktlint/detekt configuration
in CORE-01 — all present, all named in a pipeline, all doing nothing.

`scripts/lint_invariants.py` already solved this: fixtures written into a temporary root, `lint()`
run against it, each fixture asserted to produce exactly the expected number of findings, wired into
`check-repo` **before** the real run. `lint_sql.py --self-test` mirrors it exactly — same structure,
same argument, same position in the Makefile — with five fixtures: a quoted mixed-case identifier
fires, a quoted lowercase identifier fires, an allowed extension quote does not, an unindexed foreign
key fires, and a quoted identifier inside a `--` comment does not. The last is the one that matters
most: comment stripping is the part a later edit is most likely to break, and breaking it makes this
gate noisy rather than silent — which is the failure mode people route around.

Wired into `make check-db` and the CI database lane in the same change, because `docs/ci.md`'s
job ↔ local equivalence is a claim that has to stay true.

## 6. The defect: `ticket_label` binds across projects

Proving the RLS surface found one hole, and it is in the shape the boundary is meant to close.

`ticket_label` was the last two-ended association without a same-project guard. `ticket_dependency`
has the identical shape and has had its trigger since `V2`, which is what makes this an omission
rather than a decision. Its policy scopes **one** end:

```sql
create policy ticket_label_visible on ticket_label
    for all to nodera_app
    using (exists (select 1 from ticket t where t.id = ticket_label.ticket_id));
```

`label_id` is unchecked, and referential integrity checks bypass row-level security by design
(they must, or a foreign key could be evaded by hiding the parent). So `nodera_app`, holding a
context for project A alone, can attach a **project B label** to a project A ticket, and the insert
is accepted. `ticket_dependency` has a `same_project` trigger for precisely this case; `ticket_label`
had none.

What it is: an integrity breach of invariant P1 and a weak existence oracle — a caller who already
holds a label UUID learns it is real, because a genuine id succeeds where an invented one raises a
foreign key violation. What it is not: a way to read another project's data. The label's name and
colour stay invisible, and the join returns nothing.

**Corrected by `V6`, never by editing `V2`** — a new trigger mirroring `ticket_dependency_same_project`,
with a paired-negative test. `python scripts/lint_sql.py --accept` records the sixth line in the same
commit; the five existing lines are unchanged in the diff, which is the criterion.

The alternative — leaving it and filing a ticket — was rejected. `PROJECT_MANAGEMENT.md` § 8 asks
which criterion would carry a follow-up ticket, and none does: it is not a foreign subtree, not a
reserved surface, not a structural decision, not external, and nothing is deployed. It is adjacent
work in a file this package already has open, which is the definition of fix-now.

## 7. Non-goals

- **`PermissionDirectory`'s implementation.** CORE-01 left it a port and it stays one. This package
  writes no repository, no Exposed table object and no production Kotlin at all — its whole output
  is proof about the schema.
- **The REST API, the MCP tools, the frontend.** CORE-02/03, SEC-01, API-01, MCP-01.
- **Widening `lint_sql.py` beyond a self-test.** No new rule, no new convention.
- **Making the seed reusable by later packages.** It is a test fixture shaped by what these tests
  need; a shared factory designed before its second caller exists is designed for a guess.

## 8. Open questions, each with a recommendation

1. **`nodera_app` cannot create a project.** `project_visible` is `using (id = any (current_project_ids()))`
   and, with no `with check` of its own, the same expression governs insert — so the row's own id
   must already be in the context. Workable (put the new id in the context first), but nothing says
   so, and CORE-03/API-01 will meet it. *Recommendation:* pin the behaviour with a test here so it
   is documented rather than discovered, and leave the decision — owner-only project creation, or a
   `with check` that admits it — to the package that needs it. Not this one's to make.
2. **`ticket_dependency`'s policy also scopes only one end**, exactly like `ticket_label`. Its
   `same_project` trigger closes the gap, so there is nothing to fix; but the RLS layer alone does
   not hold it, which is worth knowing before anyone deletes a trigger they think is redundant.
   *Recommendation:* record it in the test's name, no change.
3. **`audit_event` rows with a null `project_id` are visible to every context.** Deliberate and
   documented in `V4` (deployment-level events, gated by `audit.read` in application code). It does
   mean RLS is not the whole boundary for that table. *Recommendation:* assert the behaviour so it is
   a decision on the record; the capability check belongs to CORE-02.
